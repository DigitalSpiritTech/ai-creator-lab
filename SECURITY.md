# Security

AI Creator Lab runs on one person's computer, with that person's own Comfy and Anthropic keys. This page says what the app does to keep those keys and that person's files safe, what it does not try to protect against, and how to report a problem.

## What the app assumes

One user. By default that user is on their own machine, reaching the app at `http://localhost:3000` (or `127.0.0.1`): `npm start` and `npm run dev` bind to `127.0.0.1` only, so nothing else on the network can reach the app, and no password is asked. The same user can choose to reach the studio from other machines (`HOST=0.0.0.0`, or a reverse proxy named in `STUDIO_ALLOWED_HOSTS`); then the app password below is required. The data folder (`.data` by default, or `STUDIO_DATA_DIR`) holds the database, every media file, exports, `secrets.json` with the saved keys, and `auth.json` with the app password's hash and the live sessions; treat a copy of it like a password file. Keys set as environment variables (`COMFY_API_KEY`, `ANTHROPIC_API_KEY`) are read on the server only.

## What is guarded

Every request, pages and API alike, goes through the request proxy (`src/proxy.ts`), and every route that changes something checks again (`assertLocalRequest` in `src/server/http.ts`). In order:

1. Host and origin. The Host must be localhost, 127.0.0.1, ::1, a name in `STUDIO_ALLOWED_HOSTS`, or the specific address in `HOST` (which stops DNS rebinding), and a request with an Origin or Sec-Fetch-Site header from another origin is refused, which stops a web page you have open from posting to the app, loading its media, or framing it. The one cross-site request allowed is a top-level navigation (a link to the app from another page), which the other page learns nothing from. These checks stay in force for signed-in requests: a session cookie does not let another site post to the app. On their own they are not authentication, since any client that can reach the port can send an accepted Host header; that is what the next step is for.
2. Read-only mode (`STUDIO_READ_ONLY=1`). Every method other than GET, HEAD, and OPTIONS is refused before a route runs, and again inside the route.
3. The app password, whenever the server is reachable from other machines: a non-loopback `HOST`, a non-loopback name in `STUDIO_ALLOWED_HOSTS`, or a non-loopback bind address in the request URL (so `next start --hostname 0.0.0.0` started by hand is caught too). Every page and API route then needs a signed-in session, except the sign-in page and its four endpoints under `/api/auth/`; build files under `/_next/static` are outside the proxy. An API call without a session gets 401, a page is sent to the sign-in page. The password is required from the server's own machine as well, because the app sees no client address it could trust. Read-only mode is the exception: it is public by design and never asks for a password, so only run it on a data folder you would show anyone. (The judging copy in `docs/DEMO-DEPLOY.md` keeps its own HTTP basic auth.)

Auth is a provider interface (`src/server/auth/provider.ts`): whether a request needs a session, which session it carries, sign-in, setup, and sign-out. The single-password provider is the only one that ships. The password is hashed with scrypt (N 2^15, r 8, p 1, a random 16-byte salt per hash) and checked with a constant-time compare; the hash lives in `auth.json` (written atomically with mode 0600). A sign-in opens a session: 32 random bytes in an `HttpOnly`, `SameSite=Strict` cookie (`Secure` when the browser reached the app over https, directly or through a proxy that sets `X-Forwarded-Proto`), of which only the SHA-256 digest is stored, so a copy of `auth.json` does not hold a usable session. Sessions last 30 days; Sign out deletes the session on the server, not only the cookie. The password, setup code, and tokens are never logged or returned in a response body. Failed sign-ins and setup attempts are answered after a one-second delay, and ten failures in ten minutes pause sign-in for everyone until the window passes (the app cannot tell clients apart, so the limit is global; sessions already open keep working). A damaged `auth.json` locks sign-in rather than opening the app.

First run on a network has no password yet, and whoever sets it owns the studio, so a stranger who reaches the port first must not be able to. The server prints a one-time setup code (100 random bits) to its own log when it starts, or when the sign-in page is first opened, and the password can only be set by someone who enters that code. Reading the server's log is something only the person running it can do, which works the same on a laptop, a home server, and a hosted container, unlike "only from loopback", which a container or a reverse proxy makes impossible to tell. Each server start prints a fresh code until a password is set; once it is, the code is gone. To reset a forgotten password, stop the server and delete `auth.json`.

Without https the password and the session cookie cross the network in the clear. On anything but a trusted home network, put the app behind a TLS proxy or reach it over a VPN.

API keys are never returned by any route or written to any log; Settings shows only whether a key is set and where it came from. The saved keys file is written atomically with mode 0600. Child processes (ffmpeg, ffprobe) run with a minimal environment that does not include the keys. `.gitignore` excludes the data folder and any `secrets.json`.

Media paths are built from UUIDs under three fixed folders inside the data folder and re-checked against the data root before any read or write. Uploads are bounded (12 MB images, 25 MB recordings), images are re-encoded through sharp with pixel limits, and recordings must be in a known audio container before ffmpeg decodes them. ffmpeg and ffprobe are always run with argument arrays (never a shell), with timeouts and output caps; caption text is escaped for both of ffmpeg's parsers. SQL is parameterized throughout. Files downloaded from Comfy Router must come over HTTPS from a public address, with redirects re-checked and a size cap.

Spending is gated twice: a generation runs only when the user clicks a proposal card (or has turned auto-approve on for proposals under their budget), and the server re-estimates the cost and refuses anything over what is left of this month's budget. The budget is monthly: the Settings value plus any amount the person added to the current period, reset on the day of the month they choose (UTC), and spend counts in the period its cost was recorded. Over all of it sits the operator ceiling, `GENERATION_ALLOWANCE_USD`, enforced on the server per calendar month (UTC) whatever the reset day, shown read-only in Settings, and zero until set; a zero ceiling blocks every paid run and every extension. "Add to this month" is a route behind the local-request check, reached only by a person's click in Settings or on the proposal card's budget dialog; it is not a tool, so neither the assistant nor the MCP server can raise a budget, and an extension can never lift the effective limit above the ceiling. The assistant can propose, archive (restorable), and revise, but cannot submit a proposal, change or extend the budget, or delete a file for good; permanent deletion is a click on the Archive page. The assistant is told that everything inside the project state is data, not instructions, which limits what a prompt injection in a brief or script can do to restorable changes.

The MCP server (`npm run --silent mcp`) offers the same tools to an MCP client, but not spending or permanent deletion unless the person starting it sets `MCP_ALLOW_SPEND=1` or `MCP_ALLOW_DELETE=1`, because an MCP client has no proposal card to click.

## What is not guarded

There is one password and one kind of user: anyone signed in has the whole studio, Settings and keys included (keys are still never shown). The sign-in limit is global, so someone who can reach the port can keep sign-in paused for new browsers, though not break into it. The app trusts its own data folder: a file replaced on disk is caught by hash when it is read, but the folder itself is yours to protect. ffmpeg decodes recordings and clips you upload; keep ffmpeg updated. Generated content goes to Comfy Cloud and Comfy Router under your key; the prompts, reference images, and voice samples a project uses leave your machine for those services. The assistant's replies come from a hosted model; the project text it reads is yours, and a bad instruction hidden in it can at most make a restorable change.

## Reporting

Open an issue on the repository with the steps that show the problem. Do not include your keys or your data folder.
